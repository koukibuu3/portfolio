## 1. 概要

### 1.1. 背景

現在のkoukibuu3.devは、技術記事を中心とした個人サイトとして運用している。

しかし、継続的な記事執筆に負担があり、更新頻度が低下している。また、技術記事の発信先としては、QiitaやZennなどの既存プラットフォームを活用した方が、読者に届く機会を得やすいと考えている。

一方で、独自ドメインのサイトは、エンジニアとしての実績・活動・価値観を表現する場所として維持・発展させたい。

そのため、技術ブログ中心の構成を見直し、キャリアと個人活動の両方を集約するポートフォリオへリニューアルする。

### 1.2. コンセプト

**つくったもの、考えたこと、歩んできたこと。**

エンジニアとしての仕事、個人開発、技術的な知見や挑戦を集約し、自分自身の現在地とこれまでの歩みを伝えるポートフォリオ。

### 1.3. 基本方針

1. **自分自身を中心に据える**
   - 技術記事よりも、人物像・実績・価値観を優先する。
   - Software EngineerとScrum Masterを重要な2つの軸として表現する。

2. **外部サービスと役割を分担する**
   - 技術記事は原則Qiita・Zennなどで発信する。
   - 各プロダクトの詳細説明はそれぞれのLPに任せる。
   - 自サイトは活動を集約し、自分自身について伝える拠点とする。

3. **更新負荷を最小化する**
   - 定期的な記事執筆を前提にしない。
   - コンテンツは最低限の情報でも公開できる。
   - 任意情報は後から段階的に充実させられる。

4. **長期的に育てられる構造にする**
   - 活動の記録を蓄積する。
   - 役割や技術的な関心の変化に対応できる構造とする。
   - 将来のコンテンツ拡張を妨げない。

## 2. サイト構成

### 2.1. グローバルナビゲーション

| ページ | パス案 | 役割 |
|---|---|---|
| Home | `/` | 人物像と主要な活動を伝える |
| Projects | `/projects` | 制作物・個人開発の実績を紹介する |
| Writing | `/writing` | 技術記事や発信活動を集約する |
| About | `/about` | 経歴・価値観・人物像を伝える |

パスは現行ルーティングとの互換性を確認して最終決定する。

### 2.2. 廃止・統合するコンテンツ

**Slides**
- 今回のリニューアルで廃止する。
- 独立ページを設けない。
- Writingにもスライド専用カテゴリを設けない。
- 既存URLについては参照状況を確認し、必要に応じてリダイレクトなどを検討する。

**Articles / Knowledge**
- Writingに統合する。
- 既存の独自ブログ記事は維持する。
- Zenn・Qiitaなどの外部記事と統一的に表示する。
- 既存記事のURLは原則維持する。変更が必要な場合はリダイレクトする。

**Activity**
- 独立ページは作成しない。
- Home内のRecent Activityとして提供する。
- 将来的に活動量が増えた場合は独立ページ化を検討する。

## 4. Projects

### 4.1. 目的

個人開発・共同開発の制作物を紹介し、どのようなものを作り、どのように関わっているかを伝える。

プロダクトの詳細機能は、それぞれのLPに任せる。

### 4.2. 初期掲載プロジェクト

| プロジェクト | 概要 |
|---|---|
| Salestack | 業務支援Webアプリケーション |
| ScrumWorkbench | スクラムイベントの準備・進行支援ツール |
| G.G. Garage | 共同ゲーム開発プロジェクト |
| Core Uma | 競馬関連の共同開発プロジェクト |

正式な説明文・技術スタック・関連URL・公開状況は、各プロジェクトの実態を確認して設定する。

### 4.3. 表示方式

**Projects一覧 + 詳細モーダル**

- 独立した詳細ページは作成しない。
- 一覧には4件すべてを掲載する。
- プロジェクトカードの選択で詳細モーダルを開く。
- モーダルから外部LPへ遷移できるようにする。

### 4.4. プロジェクト情報

**必須**
- ID / slug
- 名前
- 概要

**任意**
- カテゴリ
- サムネイル・スクリーンショット
- 開発ステータス
- 個人開発・共同開発などの開発形態
- 自分の担当範囲・役割
- 技術スタック
- プロジェクトの背景
- 技術的な工夫
- LPのURL
- GitHubなどの関連URL

任意情報が未設定の場合、その項目やセクションは表示しない。

「準備中」「Coming Soon」などのプレースホルダーは原則表示しない。

### 4.5. 詳細モーダル

**表示内容**
- 名前
- 概要
- 画像（設定されている場合）
- 開発形態・ステータス（任意）
- 技術スタック（任意）
- 自分の役割（任意）
- 外部リンク（任意）

**振る舞い**
- デスクトップでは中央配置のモーダルを基本とする。
- モバイルでは全画面ダイアログを基本とする。
- 内容が多い場合はモーダル内でスクロールできる。
- Escapeキーや閉じる操作に対応する。
- 開閉時のフォーカス管理を行う。
- 背景コンテンツへの誤操作を防止する。

**URLとの連動**

以下の形式を基本案とする。

`/projects?project=scrum-workbench`

- URLから対象モーダルを直接開ける。
- モーダルの開閉とURLを同期する。
- ブラウザの戻る・進む操作に対応する。
- Homeからも対象モーダルへ遷移できる。

### 4.6. 外部LPとの役割分担

**koukibuu3.dev**
- 何を作ったか
- 自分の担当範囲
- 使用技術
- プロジェクトの位置付け

**各プロジェクトのLP**
- 機能や特徴
- 使い方
- 詳細なサービス説明
- 利用・登録への導線

LPが存在する場合は「公式サイトを見る」を優先的な外部リンクとする。

LPがない場合もProjectsには掲載できるようにする。

### 4.7. 将来の拡張

詳細モーダルに表示する情報は、将来的な詳細ページへの移行を妨げないデータ構造とする。

ただし、今回のリニューアルでは詳細ページを実装しない。

## 5. Writing

### 5.1. 目的

技術的な知見や発信を集約し、掲載プラットフォームによらず一覧できるようにする。

### 5.2. 掲載対象

- 既存の独自ブログ記事
- Zennの記事
- Qiitaの記事

### 5.3. 表示情報

- タイトル
- 概要（取得できる場合）
- 公開日
- タグ（取得できる場合）
- 掲載元
- 記事URL

外部記事は原則、元の掲載先へ遷移する。

### 5.4. 運用方針

- 新しい技術記事は原則Zenn・Qiitaなどで公開する。
- 自サイトへの記事の二重投稿は求めない。
- 既存の独自ブログ記事は維持する。
- 掲載元を明示する。
- 新着記事は可能な範囲で自動取得する。

### 5.5. 自動取得

Zenn・Qiitaなどの公開フィードを利用した取得を検討する。

**基本方針**
- 実現可能な範囲でビルド時・定期処理による取得を行う。
- 外部サービスにアクセスできない場合でも、サイト本体の表示が破綻しないようにする。
- 記事の重複を避ける。
- 全記事を自サイトで再公開するのではなく、リンクを中心とする。

取得方法やキャッシュ方針は技術設計で決定する。

## 7. デザイン・UXの基本方針

### 7.1. デザインコンセプト

**コンテンツを中心とした、シンプルで落ち着いたポートフォリオ。**

- 過度な装飾を避ける。
- 余白とタイポグラフィを重視する。
- 画像は装飾ではなく、制作物を伝えるために使用する。
- 情報の優先順位が自然に伝わるレイアウトとする。
- 技術記事サイトよりも、個人のポートフォリオとしての印象を重視する。

色・フォント・具体的なレイアウトは別途デザイン設計で決定する。

### 7.2. レスポンシブ

デスクトップ・タブレット・スマートフォンに対応する。

特に以下を考慮する。

- ナビゲーションの操作性
- Projectsカードの配置
- 詳細モーダルの表示
- Experienceタイムラインの可読性
- 長い技術名やリンクの折り返し

### 7.3. アクセシビリティ

- キーボード操作への対応
- 適切な見出し構造
- コントラストの確保
- 画像の代替テキスト
- モーダルのフォーカス管理
- 動きの少ない表示への配慮

## 8. SEO・既存資産の扱い

### 8.1. 基本方針

検索流入自体を主な成功指標にはしない。

ただし、プロフィールや既存記事が正しく検索・共有できる状態を維持する。

### 8.2. 対応事項

- Home・Projects・Writing・Aboutに適切なタイトルと説明文を設定する。
- OGP情報を設定する。
- 既存記事のURLを原則維持する。
- URL変更時は適切なリダイレクトを設定する。
- サイトマップを整備する。
- Canonical URLを適切に設定する。
- 外部記事を二重公開しない。
- Projectsの詳細モーダルは独立した検索対象ページとして扱わない。

## 9. コンテンツ管理・更新運用

### 9.1. 基本方針

**定期更新を義務化しない。**

新しい成果や活動が生まれたときに、必要な情報を追加する。

### 9.2. 更新の契機

| 活動 | 更新内容 |
|---|---|
| 技術記事を公開 | Writingへ反映 |
| 個人プロダクトを公開 | Projectsへ追加 |
| プロダクトに重要な変更が発生 | 必要に応じて情報更新 |
| 職務や役割が変化 | Aboutを更新 |
| 公開したい活動が生まれた | Recent Activityへ追加 |

### 9.3. コンテンツの柔軟性

- 必須情報を最小限にする。
- 任意情報がなくても表示が成立する。
- 未入力セクションは表示しない。
- 最終更新日時を過度に強調しない。
- CMS導入を前提としない。
- コンテンツ管理方式は現行技術構成を踏まえて判断する。

## 14. 今回のリニューアルで目指す状態

ブログの更新頻度に依存せず、エンジニアとしての活動が蓄積されていくサイト。

訪問者は、何を作ってきたかだけでなく、どのような考え方でソフトウェアやチームに向き合っているかを理解できる。

サイトの運営者自身も、無理にコンテンツを生み出すことなく、新しい経験や成果を必要に応じて追加できる。

**長期的に育てられる、自分自身の拠点となるポートフォリオを目指す。**
